# NAS 持久化与图片存储设计

## 目标

把当前 React/Vite 单页应用改为可在 NAS 上长期运行的前后端分离应用。系统不提供登录页，前端和 API 只通过同一个 Nginx 入口访问；业务数据落到 SQLite，图片落到 NAS 文件目录。

## 已确认约束

- 保留 React 18、TypeScript、Vite 和现有页面交互。
- 后端使用 Node.js + TypeScript，部署时不向宿主机暴露后端端口。
- 不实现用户、会话或登录接口；安全边界由 NAS 局域网、VPN 和反向代理承担。
- SQLite 只保存结构化数据、状态快照和图片元数据；图片二进制保存在挂载目录。
- 现有 `localStorage` 数据自动迁移，现有 Base64 图片自动上传为文件。
- 浏览器保留本地缓存，服务器临时不可达时页面仍能读取最近一次数据；服务器恢复后，新修改继续同步。

## 方案选择

选择“版本化状态快照 + 独立媒体文件”方案，而不是立即把现有三个领域拆成大量关系表。当前前端 store 都以完整快照为边界，这个方案修改面最小，也避免为尚未稳定的字段建立复杂迁移。SQLite 中每个领域使用独立 key，后续可以逐个领域正规化而不影响 HTTP 接口。

备选方案包括：完全关系化表结构（查询能力强但迁移面大）和把 JSON 文件直接放在共享目录（简单但并发写入与事务可靠性较弱）。当前选择在改造风险、可备份性和 NAS 维护成本之间最合适。

## 架构

浏览器只访问 Nginx。Nginx 在 `/` 提供 Vite 静态文件，把 `/api/` 和 `/media/` 代理到 Node 服务。Node 服务通过 `app_state` 表读写四类快照：马克笔、个人物品、生活系统和色板；通过 `media_files` 表记录上传文件元数据。

Docker Compose 启动 `web` 和 `api` 两个容器。宿主机仅映射 Web 端口；SQLite 文件与上传目录分别绑定到 `./nas-data/database` 和 `./nas-data/uploads`，升级容器不会丢数据。

## 数据流与迁移

应用启动时并行读取四个远程快照。服务器已有数据时，以服务器为准并刷新本地缓存；服务器没有对应快照时，把当前浏览器本地快照作为首次迁移数据写入服务器。初始化完成后再渲染 React，避免先显示种子数据后闪烁。

每个 store 仍同步更新内存和 `localStorage`，同时通过短延迟合并写入远程 API。远程保存失败不会回滚本地操作，后续修改会再次尝试；启动失败则继续使用本地缓存。

旧快照中的 `data:image/...` 在写入服务器前转换成 Blob 并调用上传接口，成功后把 `imageUrl` 替换成 `/media/<uuid>.<ext>`。新选择的图片仍在浏览器端缩放压缩，再上传到服务器；开发环境 API 不可用时保留 Base64 本地兜底。

## API

- `GET /api/health`：容器健康检查。
- `GET /api/state/:key`：读取允许的状态快照；不存在时返回 404。
- `PUT /api/state/:key`：校验 JSON 后原子覆盖快照。
- `POST /api/uploads`：接收单个 `image` 文件，只允许 JPEG、PNG、WebP，最大 8 MiB，返回媒体 URL 与元数据。
- `GET /media/:filename`：读取 NAS 上传目录中的文件。

## 错误处理和安全边界

状态 key 使用白名单，JSON 请求限制为 25 MiB。上传接口同时检查 MIME、文件大小并使用 UUID 文件名，绝不使用客户端路径。SQLite 开启 WAL 与外键支持。API 不配置 CORS，因为浏览器始终同源访问。

“无登录”不等于公网匿名开放。Compose 默认只暴露 Nginx；用户应在 NAS 防火墙中限制局域网访问，远程访问使用 VPN，确需公网时再增加反向代理认证。

## 验证

后端测试覆盖快照读写、非法 key、上传校验与媒体文件落盘。前端测试覆盖初始化迁移、远程数据优先、保存队列和图片上传回退。最后运行全部 Vitest、TypeScript/生产构建，并通过本地浏览器验证启动、编辑和图片预览。
